\chapter{An\'alisis de requisitos, dise\~no e implementaci\'on}\label{requisitos}

\section{Introducci\'on}

Este cap\'itulo integra tres perspectivas que en un desarrollo profesional no deben
tratarse de forma aislada: la especificaci\'on de requisitos, el dise\~no t\'ecnico y la
implementaci\'on efectiva del sistema.

El objetivo es demostrar trazabilidad de extremo a extremo: desde la necesidad
identificada en el an\'alisis inicial hasta su materializaci\'on en componentes software,
persistencia, seguridad, pruebas y despliegue.

\section{Ecosistema de desarrollo y operaci\'on}

\subsection{Lenguajes y herramientas utilizadas}

El ecosistema t\'ecnico del proyecto se ha definido para garantizar
coherencia entre desarrollo, validaci\'on y despliegue:

\begin{itemize}
\item \textbf{Implementaci\'on backend}: Java 21, Spring Boot, Spring Security,
JPA/Hibernate, Maven y Flyway.
\item \textbf{Implementaci\'on frontend}: React, TypeScript, Vite, React Router y Axios.
\item \textbf{Documentaci\'on}: memoria en \LaTeX{} y documentaci\'on t\'ecnica auxiliar en Markdown.
\item \textbf{Gesti\'on de proyecto}: backlog y planificaci\'on iterativa
versionados en el propio repositorio.
\end{itemize}

\subsection{Pol\'itica de gesti\'on del c\'odigo fuente}

La gesti\'on del c\'odigo se realiza en repositorio Git con enfoque de ramas tem\'aticas,
integraci\'on mediante \emph{pull requests} y validaciones autom\'aticas previas a fusi\'on.
Esta pol\'itica reduce riesgo de regresi\'on,
mejora trazabilidad de cambios y permite relacionar requisitos con commits,
pruebas y despliegues.

\subsection{Estrategia de integraci\'on continua y despliegue}

La estrategia CI/CD se apoya en workflows de GitHub Actions,
con etapas separadas para backend, frontend y validaci\'on conjunta:

\begin{itemize}
\item ejecuci\'on de compilaci\'on, pruebas y lint en cada cambio relevante,
\item an\'alisis de calidad y seguridad sobre artefactos de c\'odigo,
\item construcci\'on de im\'agenes Docker y publicaci\'on automatizada,
\item despliegue en PaaS con configuraci\'on por entorno.
\end{itemize}

El objetivo operativo es que cada versi\'on candidata sea reproducible,
auditable y desplegable con esfuerzo m\'inimo,
manteniendo una l\'inea de entrega continua compatible con el calendario del TFG.

\subsection{Uso de asistentes de Inteligencia Artificial}

El proyecto adopta un uso \textbf{limitado, transparente y verificable}
de herramientas de IA generativa,
siempre como apoyo a tareas de redacci\'on preliminar,
revisi\'on o aceleraci\'on operativa,
nunca como sustituto del criterio de ingenier\'ia del autor.
El alcance y las salvaguardas aplicadas se detallan en el
Anexo D de esta memoria.

\section{An\'alisis de requisitos}

\subsection{Fuentes de requisitos}

La definici\'on del cat\'alogo de requisitos se ha construido a partir de las siguientes
fuentes:

\begin{itemize}
	\item Documento ERS (Especificaci\'on de Requisitos del Sistema).
	\item Documento DAS (Documento de An\'alisis del Sistema).
	\item Modelado estructurado y versionado en Proteus.
	\item Product Backlog y Sprint Backlog utilizados en la ejecuci\'on iterativa.
	\item Evidencia emp\'irica obtenida durante pruebas funcionales y de integraci\'on.
\end{itemize}

Este planteamiento evita una especificaci\'on est\'atica: los requisitos se formalizan,
se priorizan, se implementan por incrementos y se vuelven a validar con el producto
funcionando.

\subsection{Estructura del cat\'alogo}

El cat\'alogo se organiza en cuatro bloques complementarios:

\begin{itemize}
	\item Requisitos funcionales de informaci\'on y operaci\'on.
	\item Reglas de negocio que acotan el comportamiento permitido.
	\item Requisitos no funcionales de calidad del sistema.
	\item Restricciones e integraciones t\'ecnicas por entorno.
\end{itemize}

En Proteus se distinguen expl\'icitamente requisitos funcionales (por ejemplo,
\texttt{RQF-001}), reglas de negocio (\texttt{REGN-001}) y no funcionales
(\texttt{RQNF-001} a \texttt{RQNF-011}), lo que facilita su seguimiento
durante la implementaci\'on.

\subsection{Requisitos funcionales}

El ERS define un abanico funcional amplio, del que se ha priorizado el n\'ucleo
necesario para el MVP. A nivel de dominio, la funcionalidad se agrupa en:

\begin{enumerate}
	\item \textbf{Identidad y acceso}: autenticaci\'on de usuarios y control por rol.
	\item \textbf{Estructura acad\'emica}: cursos, grupos, actividades y vinculaciones.
	\item \textbf{Gesti\'on de entregables}: configuraci\'on de fechas, visibilidad,
	reenv\'ios y estructura esperada.
	\item \textbf{Gesti\'on de entregas}: subida, historial, descarga y trazabilidad.
	\item \textbf{Evaluaci\'on y feedback}: calificaci\'on, comentarios y publicaci\'on de notas.
\end{enumerate}

Como ejemplos representativos:

\begin{itemize}
	\item \textbf{RQF-001}: creaci\'on de usuarios por administrador.
	\item \textbf{RQF-014--RQF-017}: operaciones de entrega y versionado.
	\item \textbf{RQF-018--RQF-025}: evaluaci\'on, visibilidad e integraciones.
\end{itemize}

\subsection{Reglas de negocio}

Las reglas de negocio restringen de forma expl\'icita qu\'e acciones son admisibles.
Una regla clave es \textbf{REGN-001}, que establece que solo el profesor
autorizado puede asignar una calificaci\'on.

Esta norma se implementa en validaciones de servicio y controlador,
evitando tanto la elevaci\'on de privilegios como la evaluaci\'on fuera de contexto
(p. ej., docente no vinculado al grupo o actividad).

\subsection{Priorizaci\'on y alcance}

La priorizaci\'on se realiz\'o con criterio MoSCoW y validaci\'on continua con el backlog.
El foco del MVP se situ\'o en los procesos con mayor impacto docente:

\begin{itemize}
	\item gesti\'on de actividades y entregables,
	\item flujo completo de entrega y evaluaci\'on,
	\item seguridad por rol,
	\item persistencia y trazabilidad de cambios.
\end{itemize}

Funcionalidades avanzadas (integraciones extendidas, autenticaci\'on federada completa,
observabilidad m\'as profunda) se mantienen en backlog de evoluci\'on y no comprometen
la viabilidad del alcance de TFG.

\subsection{Contexto documental de partida (ERS y DAS)}

La especificaci\'on documental de este TFG no se apoya en descripciones ad hoc,
sino en dos artefactos de an\'alisis formal mantenidos en Proteus:

\begin{itemize}
	\item \textbf{ERS (Especificaci\'on de Requisitos del Sistema)}:
	define situaci\'on actual, necesidades de negocio, subsistemas y cat\'alogo
	de requisitos (generales, de informaci\'on, funcionales, no funcionales y
	reglas de negocio).
	\item \textbf{DAS (Documento de An\'alisis del Sistema)}:
	define arquitectura l\'ogica, modelo de clases, diagramas de estado,
	diagramas de secuencia, navegabilidad e inventario de mockups de interfaz.
\end{itemize}

La reutilizaci\'on de ambos documentos en esta memoria persigue dos objetivos:
primero, preservar trazabilidad respecto al trabajo original de Ingenier\'ia
de Requisitos; segundo, demostrar que las decisiones de dise\~no e implementaci\'on
adoptadas durante el TFG responden a una base de especificaci\'on expl\'icita.

\subsection{Situaci\'on actual y necesidades de negocio (ERS)}

El ERS identifica un escenario de partida con fricci\'on operativa notable:
creaci\'on de actividades y recogida de entregas con alto componente manual,
dificultad para mantener trazabilidad uniforme y baja capacidad de evoluci\'on
cuando se pretende introducir reglas de negocio m\'as finas.

Sobre ese diagn\'ostico, las necesidades de negocio priorizadas fueron:

\begin{itemize}
	\item reducir carga administrativa en procesos docentes recurrentes,
	\item dar al estudiante un flujo de entrega m\'as guiado y transparente,
	\item centralizar evaluaci\'on y feedback con reglas de autorizaci\'on claras,
	\item mejorar mantenibilidad del sistema y su capacidad de evoluci\'on.
\end{itemize}

Estas necesidades se conectan con el resto de la memoria en tres planos:
arquitectura (separaci\'on de capas), implementaci\'on (m\'odulos especializados)
y verificaci\'on (pruebas por flujo cr\'itico y por requisito).

\section{Dise\~no del sistema}

\subsection{Arquitectura de alto nivel}

La arquitectura adoptada es cliente-servidor desacoplada:

\begin{itemize}
	\item \textbf{Frontend SPA} en React + TypeScript (presentaci\'on y experiencia de usuario).
	\item \textbf{Backend REST} en Spring Boot (l\'ogica de negocio y seguridad).
	\item \textbf{Persistencia relacional} con JPA/Hibernate y migraciones Flyway.
\end{itemize}

En backend se aplica dise\~no por capas
(controller, service, repository y entity),
que mejora mantenibilidad, testabilidad y capacidad de evoluci\'on.

\subsection{Vista de despliegue}

La vista de despliegue se organiza en cuatro bloques principales:

\begin{itemize}
\item \textbf{Cliente web}: navegador del usuario final (profesor, estudiante o administrador).
\item \textbf{Frontend}: SPA est\'atica servida desde plataforma PaaS (Render).
\item \textbf{Backend}: API REST desplegada como servicio web Docker en Render.
\item \textbf{Datos}: base de datos PostgreSQL gestionada y accesible solo desde backend.
\item \textbf{Servicios externos}: almacenamiento cloud, OneDrive y correo transaccional por API HTTP.
\end{itemize}

La separaci\'on de componentes permite escalar y evolucionar cada capa
sin romper el resto del sistema,
manteniendo adem\'as una frontera de seguridad clara entre cliente,
l\'ogica de negocio y persistencia.

\begin{table}[ht]
\centering
\begin{tabular}{|P{2.9cm}|P{3.1cm}|P{5.6cm}|}
\hline
\textbf{Nodo} & \textbf{Tecnolog\'ia} & \textbf{Responsabilidad principal} \\

Cliente & Navegador moderno & Interacci\'on de usuario y consumo de API sobre HTTPS. \\
\hline
Frontend & React + Vite en Render & Renderizado de interfaz, estado de sesi\'on y experiencia por rol. \\

\subsection{Dise\~no de dominio y datos}

El dominio se modela alrededor de la relaci\'on docente-estudiante-actividad:

\begin{itemize}
	\item \texttt{Usuario} como identidad base.
	\item \texttt{Profesor} y \texttt{Estudiante} como especializaciones operativas.
	\item \texttt{Curso}, \texttt{Grupo} y \texttt{Actividad} para contexto acad\'emico.
	\item \texttt{Entregable} y \texttt{Entrega} para el ciclo de entrega.
	\item \texttt{Feedback}, \texttt{Material} y entidades de soporte (tokens, notificaciones).
\end{itemize}

La persistencia evoluciona de forma versionada mediante migraciones,
lo que permite incorporar nuevas capacidades sin perder consistencia hist\'orica.

\subsection{Dise\~no de API}

La API sigue orientaci\'on REST y separa contratos mediante DTOs.
Se definen m\'odulos de endpoint coherentes por contexto de negocio:

\begin{itemize}
	\item \texttt{/api/auth}: login, refresh, recuperaci\'on de contrase\~na.
	\item \texttt{/api/actividades}: gesti\'on de actividades y consulta por usuario.
	\item \texttt{/api/entregables}: administraci\'on de entregables.
	\item \texttt{/api/entregas}: subida, revisi\'on, evaluaci\'on y descarga de entregas.
\end{itemize}

El uso de DTOs evita exponer directamente entidades de persistencia,
reduce acoplamiento y simplifica evoluciones de contrato.

\subsection{Dise\~no de seguridad}

El dise\~no de seguridad incorpora mecanismos complementarios:

\begin{itemize}
	\item autenticaci\'on basada en JWT (token de acceso + refresh token),
	\item filtros de validaci\'on en la cadena de seguridad,
	\item autorizaci\'on por rol y contexto acad\'emico,
	\item cifrado de contrase\~nas con BCrypt,
	\item limitaci\'on de tasa en operaciones sensibles de autenticaci\'on.
\end{itemize}

Se configura CORS de forma expl\'icita y se diferencia entre rutas p\'ublicas y protegidas,
minimizando superficie de ataque sin comprometer usabilidad.

\subsection{Dise\~no del frontend}

El frontend se organiza en m\'odulos \texttt{pages}, \texttt{components}, \texttt{context}
y \texttt{services}, con los siguientes objetivos:

\begin{itemize}
	\item experiencia coherente para profesor y estudiante,
	\item protecci\'on de rutas seg\'un sesi\'on y rol,
	\item gesti\'on centralizada de autenticaci\'on,
	\item manejo uniforme de errores y estados de carga.
\end{itemize}

La capa de red encapsula llamadas HTTP y gesti\'on de tokens,
incluyendo renovaci\'on autom\'atica de sesi\'on al expirar el token de acceso.

\section{Implementaci\'on}

\subsection{Implementaci\'on backend}

La implementaci\'on backend se estructura en el paquete principal de la aplicaci\'on,
donde destacan:

\begin{itemize}
	\item \textbf{Controladores}: entrada HTTP y validaci\'on de contratos.
	\item \textbf{Servicios}: l\'ogica de negocio y reglas del dominio.
	\item \textbf{Repositorios}: acceso a datos con Spring Data JPA.
	\item \textbf{Seguridad}: configuraci\'on central y filtros especializados.
\end{itemize}

Un punto clave es \texttt{EntregaService}, que centraliza validaciones de entrega,
control de versiones, restricciones temporales y operativa de evaluaci\'on,
con apoyo de servicios auxiliares para materiales y notificaciones.

\subsection{Implementaci\'on de flujos cr\'iticos}

Los flujos con mayor impacto funcional son:

\begin{enumerate}
	\item \textbf{Autenticaci\'on y sesi\'on}:
	login, emisi\'on de tokens, refresco y cierre seguro de sesi\'on.
	\item \textbf{Publicaci\'on de entregables}:
	creaci\'on por docente, configuraci\'on de fechas y condiciones de entrega.
	\item \textbf{Entrega de material}:
	subida de ficheros, verificaciones, versionado y almacenamiento de metadatos.
	\item \textbf{Evaluaci\'on}:
	correcci\'on por profesor autorizado, feedback y visibilidad de nota.
\end{enumerate}

Cada flujo incorpora validaciones de entrada, control de errores y verificaci\'on de permisos,
asegurando consistencia en escenarios concurrentes y previniendo acciones fuera de alcance.

\subsection{Implementaci\'on frontend}

La implementaci\'on del cliente cubre pantallas y operaciones necesarias para el MVP:

\begin{itemize}
	\item acceso y gesti\'on de sesi\'on,
	\item paneles de actividades y entregables,
	\item formularios de entrega y seguimiento,
	\item vista de evaluaciones y retroalimentaci\'on.
\end{itemize}

Se han introducido medidas pr\'acticas para mejorar usabilidad:
mensajes de validaci\'on temprana, estados visuales de proceso,
y comportamiento resiliente ante errores de red.

\subsection{Persistencia, migraciones e integraciones}

Se utiliza PostgreSQL en escenarios de despliegue y un perfil de desarrollo
local para iteraci\'on r\'apida. Flyway gestiona la evoluci\'on del esquema,
incluyendo ampliaciones como:

\begin{itemize}
	\item atributos para validaci\'on estructural de entregas ZIP,
	\item campos para integraci\'on cloud (OneDrive/Cloudinary),
	\item tablas y preferencias de notificaci\'on,
	\item tokens de recuperaci\'on de contrase\~na.
\end{itemize}

Las integraciones externas se dise\~nan por configuraci\'on,
de modo que el sistema puede operar en local sin dependencia obligatoria
de servicios de terceros.
En producci\'on el env\'io de correos se realiza mediante Brevo a trav\'es
de peticiones HTTPS, evitando depender del protocolo SMTP, que puede estar
restringido en plataformas PaaS. Este canal se utiliza para recuperaci\'on
de contrase\~na y notificaciones transaccionales.

\subsection{Verificaci\'on de implementaci\'on}

La verificaci\'on se realiza en capas (unitaria, integraci\'on, E2E y mutaci\'on),
apoyada por pipelines CI/CD y controles de seguridad en preproducci\'on.
Este enfoque proporciona evidencia objetiva de robustez y reduce el riesgo de regresiones.

\section{Discusi\'on t\'ecnica}

\subsection{Decisiones y compromisos}

Las decisiones principales del dise\~no implican compensaciones expl\'icitas:

\begin{itemize}
	\item \textbf{Separaci\'on SPA + API}: mejora mantenibilidad y escalado,
	con mayor esfuerzo de orquestaci\'on y pruebas de integraci\'on.
	\item \textbf{JWT con refresh token}: simplifica backend stateless,
	pero exige controles cuidadosos de expiraci\'on y renovaci\'on.
	\item \textbf{DTOs y capas}: reducen acoplamiento,
	a costa de mayor c\'odigo estructural.
	\item \textbf{Migraciones versionadas}: aportan trazabilidad de datos,
	requiriendo disciplina de despliegue entre entornos.
\end{itemize}

\subsection{Limitaciones y trabajo futuro}

Aunque el n\'ucleo funcional est\'a cubierto, se identifican l\'ineas de evoluci\'on:

\begin{itemize}
	\item ampliaci\'on de autenticaci\'on avanzada (p. ej., 2FA completa),
	\item observabilidad m\'as profunda con m\'etricas operativas,
	\item cierre progresivo de requisitos \emph{Should/Could} pendientes.
\end{itemize}

Estas mejoras no condicionan la validez del TFG,
sino que delimitan una hoja de ruta t\'ecnica razonable para continuidad del proyecto.

\section{Conclusiones del cap\'itulo}

El an\'alisis realizado demuestra coherencia entre lo especificado y lo implementado.
Los requisitos funcionales priorizados se traducen en flujos operativos reales,
los no funcionales se abordan mediante decisiones t\'ecnicas concretas,
y el dise\~no modular facilita mantenimiento, verificaci\'on y evoluci\'on.

Por tanto, el resultado no es solo una implementaci\'on funcional,
sino una soluci\'on con fundamento de ingenier\'ia de software,
alineada con los objetivos acad\'emicos y profesionales del TFG.
